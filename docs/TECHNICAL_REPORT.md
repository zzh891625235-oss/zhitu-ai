# 第一章 项目概述

## 1.1 选题背景

高校里流传着一句话："大学四年，最怕的不是忙，是不知道为什么忙。"这句话背后是三个长期存在却没人系统性解决的问题：

**第一，成长路径没有被显式化。** 大一到大四每个阶段该做什么，多数学生只能从学长学姐的经验贴里拼凑。这些信息零散、过时，且与自己的专业不一定相关——一个自动化专业的学生照着计算机专业的攻略准备，很可能在大三才发现方向不对。

**第二，计划与执行之间断开了。** 制定计划不难，难的是坚持。而现有的效率工具只记录"做了没有"，没有人会根据你的完成情况反过来调整计划本身。

**第三，AI 建议不可信也逐渐不被信任。** 通用大模型能给出一份看起来很像样的大三规划，但它不知道你是哪个专业、GPA 多少、哪门课还没过。更危险的是，它会一本正经地推荐不存在于任何官网的竞赛。学生问两次发现对不上，就再也不用了。

本作品要解决的就是这三件事：**把路径显式化、让计划能被数据驱动地调整、让 AI 的建议始终能追溯到真实数据。**

## 1.2 作品定位

智途AI 是一个面向在校大学生的 AI Native 成长规划 Web 应用。它的核心不是"一个会聊天的 AI"，而是：

> 一个**会自己去查数据、会用资料支撑结论、并且把依据摆给用户核对**的成长 Agent。

具体落地为一条完整闭环：

```
采集学情 → AI 生成画像 → AI 生成四年规划 → 每日执行打卡
   → AI 读取执行数据重排计划 → 沉淀成长档案 → 生成求职简历 → 模拟面试
```

## 1.3 目标用户

| 用户 | 场景 | 核心诉求 |
| --- | --- | --- |
| 大一学生 | 刚入学，专业认知模糊 | 了解本专业的课程地图与成长节奏 |
| 大二学生 | 需要积累竞赛与项目经历 | 知道该报哪个比赛、做什么项目 |
| 大三学生 | 就业 / 考研 / 保研分流 | 得到有具体时间节点的行动清单 |
| 大四学生 | 秋招、考研冲刺 | 简历有内容可写、面试答得上来 |

覆盖范围刻意拓展到 **175 个专业**而不只是计算机类。这一点是刻意设计的：非计算机专业的学生恰恰是最缺乏针对性指导的群体，而市面上绝大多数学习类工具默认用户是程序员。

# 第三章 系统架构设计

## 3.1 总体架构

系统采用前后端分离架构，AI 能力集中在后端一个独立分层的 `ai` 包中，前端通过事件流消费 AI 的中间过程。

```
┌──────────────────────── 视图层 ────────────────────────┐
│  Vue 3 + Vite 5  ·  Pinia  ·  Vue Router 4            │
│  Element Plus  ·  ECharts  ·  Axios + fetch 流式读取    │
│  AppBackground(Canvas 动态背景) · AgentTrace(思考可视化) │
└──────────────────────────┬─────────────────────────────┘
                           │ JWT Bearer · NDJSON 事件流
┌──────────────────────────▼─────────────────────────────┐
│  Spring Boot 2.7  ·  Spring Security + JWT            │
│  Controller → Service → MyBatis-Plus                  │
│  ┌────────────── AI 层 ────────────────┐              │
│  │ AgentRuntime   ReAct 编排（≤4 轮）    │              │
│  │ ToolRegistry   8 工具 → OpenAI tools │              │
│  │ RagService     BM25 + 哈希向量混合    │              │
│  │ AiGuard        注入/幻觉/JSON 修复    │              │
│  │ PromptLibrary  统一人设与诚实性约束   │              │
│  │ AIService      厂商无关抽象           │              │
│  └─────────────────────────────────────┘              │
└──────────┬───────────────────────────────┬─────────────┘
           │                               │
    ┌──────▼───────┐          ┌────────────▼───────────┐
    │ MySQL8 / H2  │          │ 大模型（OpenAI 兼容协议）│
    │   13 张表     │          │ DeepSeek / 通义 / OpenAI│
    └──────────────┘          └────────────────────────┘
                   │
          ┌────────▼────────┐
          │ MCP Server(node) │  对外暴露同样 9 个工具
          └──────────────────┘
```

## 3.2 前端架构

| 关注点 | 做法 |
| --- | --- |
| 组件划分 | 视图层 13 个页面；可复用 UI 抽到 components（动态背景、Agent 轨迹、图片录入、语音条） |
| 状态管理 | Pinia 管理登录态；页面内状态就近用组合式 API 持有，避免过度集中 |
| 路由 | Vue Router 4，全部页面动态 import 懒加载，路由标题统一由 meta 驱动 |
| 网络层 | Axios 统一拦截 401 与错误提示；AI 流式接口单独用 fetch 读取 ReadableStream |
| 流式渲染 | 增量字符串追加 + 自研轻量 Markdown 渲染器，避免引入完整 md 解析库 |
| 性能优化 | manualChunks 拆分为 vendor-core / vendor-element / vendor-echarts；CSS 按 chunk 分割；移除 5.5MB 无用静态资源 |

## 3.3 数据模型

共 13 张表，核心实体关系如下：

```
user ──1:1── user_settings        （用户级 AI 配置，Key 优先级高于系统配置）
  │
  ├──1:1── student_profile ──N:1── major
  │                    └── 1:1 ── ai_portrait（画像文本存在档案表中）
  │
  ├──1:N── learning_record ──N:1── course ──N:1── major
```

## 3.4 一次 Agent 问答的时序

```
学生              前端                 后端 AgentRuntime            工具/知识库
 │  提问   │        │  POST /agent/chat-stream │        │
 ├────────►│───────►│────────────────────────►│        │
 │         │        │                         │ 护栏校验│
 │         │        │◄─── status 检索中 ──────┤        │
 │         │        │                         ├───────►│ RAG 检索
 │         │        │◄─── citations ──────────┤◄───────┤
 │         │        │◄─── tool_call ──────────┼───────►│ 执行工具（带 userId）
 │         │        │◄─── tool_result ────────┤◄───────┤

 │         │        │◄─── done ───────────────┤        │
```

把中间过程全部暴露出来，是这个架构最重要的一个决定：**AI 的思考过程对使用者不再是黑盒。**

# 第四章 AI 技术方案

这是本作品投入最重的部分。下面按技术点逐一说明。

## 4.1 设计出发点：为什么必须是 Agent

最容易的做法是把学生档案拼成一段文本塞进 Prompt，让模型直接回答。我们否决了它，原因有三：

1. **无法知道模型到底用了哪些数据。** 它可能看了你的 GPA，也可能完全没看。生成过程不可观测。
2. **数据一旦变更就要重发整段 Prompt**，上下文成本随字段数线性增长，而实际上一次问答通常只需要两三个维度。
3. **模型没有被强制使用真实数据。** 它完全可以忽略你给的上下文，凭参数记忆回答。

改为工具调用之后：

- 模型必须**显式声明**"我要查什么"，这一步本身就产生了可观测的决策记录；
- 工具执行结果以 JSON **原样回灌**进消息历史，模型写进答案的每个数字都能对应到某次工具调用；
- 数据在调用时才读取，永远是最新值，而且**只取本次真正需要的字段**。

## 4.2 大模型集成

### 4.2.1 厂商无关抽象

全部 AI 能力只依赖一个接口 `AIService`，目前唯一实现是 `DeepSeekProvider`（OpenAI Chat Completions 协议）。切换厂商只需改 `application.yml` 中的三行配置，业务代码零改动。

支持的能力包括：普通对话、带用户 Key 的对话、流式对话、**带工具声明的对话**、**多模态图像理解**、服务状态上报。

### 4.2.2 三个稳定性设计

**(1) Key 的优先级链**

```
学生自己的 Key（API 设置页）  >  系统 Key（环境变量）
```

这让没有 Key 的评审者可以直接体验内置离线模式，而希望看到真实大模型效果的用户可以自行接入，互不干扰。

**(2) 诚实降级**

调用失败重试耗尽后自动降级到规则编排，并通过 `/api/ai/status` 的 `lastCallReal` 字段如实上报。前端据此显示"离线模板模式"标签。

这里有一条贯穿全项目的原则：**绝不把模板结果伪装成 AI 生成。** 学生要依据这些建议做决策，把降级结果说成是大模型的判断，比功能不可用危害更大。

**(3) 工具能力探测**

部分模型或中转网关不认识 `tools` 字段，会返回 400。此时自动把 `toolsSupported` 置 false，后续直接走规则编排，避免每条消息都白白多打一次网络请求。

### 4.2.3 Prompt 工程

所有 Prompt 集中在 `PromptLibrary` 统一管理，好处是改文案不必翻业务代码，也便于评审直接看到"AI 是怎么被约束的"。核心提示词包含四层：

1. **场景人设**：通用 / 学习导师 / 职业规划 / 竞赛辅导 / 模拟面试，并把专业方向写进开头 `【专业:xxx】`，让离线兜底也能解析出方向；
2. **诚实性约束（最高优先级）**：只能使用资料中出现过的信息；资料里没有就直接说没有；涉及具体数据必须标注来源编号；档案没填就引导去填，不要假设；
3. **工具阶段的专用指令**：要求模型在这一轮只做决策（调用哪些工具），信息足够时才直接回答，禁止重复调用相同参数的工具；
4. **收束阶段的合成指令**：给结论 → 给理由 → 给"下一步具体做什么"，引用用方括号数字，全文控制在 600 字以内。

## 4.3 Agent 工作流

### 4.3.1 五阶段流水线

| 阶段 | 产出事件 | 说明 |
| --- | --- | --- |
| 0 护栏校验 | `blocked` | 注入与违规内容检测，不通过即终止 |
| 1 RAG 检索 | `citations` | 从本地知识库取回带编号的资料片段 |
| 2 工具循环 | `mode` `tool_call` `tool_result` | 模型自主决定（或规则编排），最多 4 轮 |
| 3 合成答案 | `status` `delta` | NDJSON 流式推送正文 |
| 4 事实校验 | `verify` `done` | 比对答案中的专名与资料源 |

### 4.3.2 工具清单

| 工具 | 读取的数据 | 典型触发问题 |
| --- | --- | --- |
| `get_student_profile` | 学籍档案 | "我是 xx 专业大二的，该…" |
| `get_ability_portrait` | 九维能力自评与画像 | "我哪方面比较弱" |
| `list_courses_with_progress` | 课程地图 + 进度 | "下一步该学什么" |
| `search_bilibili_courses` | B 站公开课资源库（262 门） | "高数去哪学"、"推荐个 Python 入门课" |
| `find_competitions` | 竞赛库（专业过滤） | "该报哪个比赛" |
| `get_study_progress` | 打卡记录 | "我执行得怎么样" |
| `get_growth_records` | 成长档案 | "简历能写什么" |
| `search_knowledge_base` | RAG 知识库 | "保研流程是怎样的" |
| `get_four_year_plan` | 已生成的四年规划 | "接下来做什么" |

三条硬性约束：

- 工具**全部只读**，Agent 不能擅自修改用户数据；
- `userId` 贯穿所有查询，天然实现数据隔离；
- 工具内部出错时返回人类可读的错误说明而不是抛异常，让模型知道可以换条路。

`search_bilibili_courses` 是第 9 个工具，服务于"学习资源闭环"：课程地图告诉学生**该学什么**，B 站工具告诉学生**去哪学**。它检索平台人工梳理的 262 门公开课（标题 / UP 主 / 难度 / 推荐理由 / 链接，覆盖 13 个类别与 175 个专业），支持关键词模糊命中（标题、UP 主、keywords 三字段），无关键词时按学生专业返回对口推荐（与页面推荐共用 `CourseMajorRelevance` 与 `BilibiliRecommendPolicy`，两处给出的课程顺序与层级完全一致）。返回的链接会出现在「查看依据」卡片中可点击溯源——AI 推荐的课程不是模型记忆里的编号，而是资源库中真实存在的条目。

### 4.3.3 双引擎与降级

```
               ┌──────── 大模型可用 ────────►  LLM_DRIVEN
               │                              模型自主选择工具
  一次提问 ────┤
               │                              ┌ 关键词规则判断意图
               └──────── 大模型不可用 ──────►  ├ 仍然执行真实工具
                          RULE_DRIVEN          └ 用真实数据合成答案
```

关键在于：**降级降的是"谁来选工具"，不是"有没有数据"。** 推荐引擎给这名学生看的竞赛，在两条链路上都来自同一张数据库表。

### 4.3.4 多轮对话记忆

真实使用中学生一定会追问："那第一个什么时候开始报名？""跟第二个比哪个更适合我？"这类问题离开上文毫无意义，因此 Agent 必须是有记忆的。

实现方式（`AgentRuntime.loadHistory`）：

1. 每轮开始前，从 `ai_chat` 表按用户与场景取最近 **3 轮**（6 条消息），按时间正序注入模型上下文；
2. 单条历史截断至 **300 字符**——历史的作用是让模型知道"刚才聊过什么"，不是全文复述，截断控制 token 成本；
3. 历史加载失败只降级为"无记忆模式"，绝不让对话崩溃；
4. 前端会收到 `memory` 阶段事件，用户能看到"已带入最近 N 轮对话记忆"。

**实测**：第一轮问"我这个专业有哪些对口竞赛"后，追问"那第一个什么时候开始报名？"，模型正确理解"第一个"指向第一轮回答中的蓝桥杯，并如实说明"平台赛事库不含报名起止日期"而没有编造——记忆与防幻觉同时生效。

## 4.4 RAG 检索增强

### 4.4.1 语料

| 来源 | 数量 | 更新方式 |
| --- | --- | --- |
| 竞赛库 | 101 场 | 数据库记录，启动时抽取 |
| 课程库 | 3941 门 | 数据库记录，启动时抽取 |
| 专业库 | 175 条 | 数据库记录，启动时抽取 |
| 人工方法语料 | 15 篇 | `rag/corpus.md`，改文件不需要改代码 |

合计 4200+ 片段。

### 4.4.2 检索流程

```
查询 → 分词（中文二元组 + 英文单词）
     → BM25 打分（IDF × TF 饱和 × 长度归一）  权重 0.55
     → 哈希向量余弦（128 维，次线性 TF 加权）   权重 0.45
     → 专业相关性加权（命中本人专业 +0.15）
     → 阈值过滤（<0.06 丢弃，避免污染 Prompt）
     → 取 Top-4 渲染成带编号的 Markdown 块
```

**为什么不用现成的向量数据库或分词器？** 一是评审复现成本——多一个外部服务就多一个启动失败的可能；二是这套方案在最坏情况下只需要几百 KB 内存、毫秒级完成索引构建，且完全离线。字符二元组对中文子词匹配的效果，在我们这个语料规模上并不逊色于分词后再匹配。

### 4.4.3 引用溯源

Prompt 中明确要求模型用 `[n]` 标注出处，前端同时把本次真正命中的片段渲染成"参考来源"卡片（来源类型、标题、相关度、摘要）。用户可以直接点开逐条核对——这是本作品处理 AI 可信度的主要手段。

## 4.5 多模态能力

### 4.5.1 图像理解：证书拍照录入

```
选择图片 → Base64 → 视觉模型抽取字段 → 摊开成表单让用户核对 → 确认入库
```

设计上有两道刻意保留的"人工确认"：

1. 抽出的字段一定先摊给用户改，不在后台静默写库；
2. 置信度低于 0.6 时给出醒目提示。

简历是要拿去求职的，一条张冠李戴的获奖记录代价远高于多敲三十秒键盘。

更重要的是失败路径的处理：**模型返回 null（不支持视觉 / 未配 Key）时，如实返回"不可用"并给出空白表单让用户手动填，绝不根据文件名去猜这是一张三好学生奖状。**

### 4.5.2 语音输入与朗读

采用浏览器原生 Web Speech API：

- 识别在浏览器本地完成，朗读交给系统语音合成引擎；
- **学生的语音数据不会离开本机**，也不需要部署任何 ASR / TTS 服务；
- 朗读前会剥离 Markdown 记号，否则会把星号和井号一起念出来；
- Firefox 不支持 SpeechRecognition，此时按钮自动禁用并给出说明，而不是假装能用。

## 4.6 MCP 与 Function Calling

`ToolRegistry` 一份定义，两套协议出口：

- `openAiTools()` —— OpenAI Function Calling 的 `tools` 数组，服务于内部 Agent；
- `manifest()` —— MCP `tools/list` 形态（`GET /api/agent/tools`），字段对齐 `inputSchema`。

此外，`mcp-server/` 是一个**可运行的标准 MCP Server**（Node，stdio JSON-RPC，约 150 行），实现了 `initialize`、`tools/list`、`tools/call`、`ping`。它把同样这 9 个工具暴露给 Claude Desktop、Cursor 等任意 MCP 客户端。

这里有一个刻意的架构决定：**MCP Server 不含任何业务逻辑，只做协议转换。** 工具实现、数据权限、防幻觉校验始终只有后端一份，不会出现"改了后端，MCP 这边还留着旧逻辑"这种两套代码各自漂移的情况。

```json
{ "mcpServers": {
    "zhitu-ai": {
      "command": "node",
      "args": ["绝对路径/mcp-server/index.js"],
      "env": { "ZHITU_BASE_URL": "http://localhost:8080", "ZHITU_TOKEN": "eyJ..." }
    } } }
```

需要注意的是，MCP 要求"工具执行失败"也要返回正常响应加 `isError` 标记，而不是抛协议错误——这样模型能看到失败原因并自行决定重试还是换条路。

## 4.7 AI 安全与可控性

| 风险 | 对策 | 实现位置 |
| --- | --- | --- |
| Prompt 注入 | 8 条中英文注入特征正则 | `AiGuard.verifyInput` |
| 违规内容请求 | 违法 / 暴力 / 自伤 / 作弊代写关键词拦截 | 同上 |
| Prompt 被撑爆 | 输入截断至 2000 字 | `MAX_QUESTION_LENGTH` |
| 密钥复读 | 出口抹掉 `sk-*`、Bearer、手机号 | `AiGuard.maskSecrets` |
| 模型幻觉 | 专名与资料做"3 字连续重合"比对 | `AiGuard.suspectClaims` |
| 输出不是合法 JSON | 代码块剥离 → 花括号截取 → 带错误回传的自修复重试 | `AiGuard.extractJson` |
| 推荐假赛事 | 推荐强制来自数据库与推荐引擎 | `CompetitionTool` |
| 把模板当 AI 结果 | `lastCallReal` 如实上报，前端展示标签 | 全局 |
| 接口被刷 / 额度被烧 | 滑动窗口限流：每用户每分钟 10 次，超限返回含等待时长的提示 | `AgentRateLimiter` |
| 知识库未命中却假装有依据 | 零命中时前端明确提示"以上来自通用知识" | `AgentTrace` |

### 4.7.1 幻觉检测的具体做法

模型答案中的每一处"像专名的说法"（以大赛 / 锦标赛 / 挑战赛 / 竞赛 / 联赛 / 杯 等结尾）会被抽取出来，与本次工具返回 + RAG 命中的所有事实来源比对。判定"有出处"的条件是：完全相等、互相包含，或**最长公共子串 ≥ 3 字**。

之所以要求 3 字而不是"有交集"，是因为单字双字的偶然重合在中文里太常见了，放宽标准等于形同虚设。同时用停止词表过滤掉"我从平台竞赛库里筛出了……"这类泛指表达。

检出的疑似说法不做删除（那会让答案读不通），而是在前端以警示条形式列出："有 N 处说法未在资料库中命中，请自行核实"。

### 4.7.2 可解释性

三条链路交织：

1. **工具轨迹**——AI 调用了哪些工具、每个工具返回了什么，逐条展示；
2. **引用来源**——本次用到的知识片段，带相关度评分；
3. **事实校验**——答案是全部有出处，还是有几处需要核实。

## 4.8 成本与性能优化

| 措施 | 效果 |
| --- | --- |
| 工具阶段温度设为 0.2 | 结构化决策更稳定，减少重复调用 |
| 模型不支持 tools 时自动关闭开关 | 避免每次对话空跑一次请求 |
| 图像理解不做重试 | 图像 token 成本高，失败直接引导手动填写 |
| 单次问答工具轮次上限 4 | 兜住模型陷入循环的风险 |
| Prompt 只注入 Top-4 片段且单片段截断 320 字 | 控制上下文长度 |
| RAG 阈值过滤 | 低相关片段不进 Prompt，节省 token 也避免干扰 |

# 第五章 核心功能实现

## 5.1 AI 学生画像

学生完成九项能力自评后，后端把自评等级、GPA、目标方向组织成结构化输入，要求模型输出多维度评估、优势、短板与三个月行动建议。输出不稳定时用 `AiGuard.extractJson` 修复，仍失败则回退到基于规则的画像，**并在前端标注这一次不是大模型输出**。

## 5.2 AI 四年规划

按就业 / 考研 / 保研 / 考公四种发展方向分别生成大一至大四的分阶段规划（目标、核心课程、技能、推荐竞赛、风险提醒）。

实现上有一个针对性设计：`MajorDirection` 把 175 个专业映射到 19 个方向，每个方向有自己的课程侧重、证书与岗位。这解决了一系列真实的偏差问题：

- 早期版本中，统计学学生会被告知去参加地质技能竞赛，因为它们在同一个"理学"大类下。修复方式是匹配分三档：`EXACT`（精确列出该专业）> `OPEN`（不限专业）> `RELATED`（同方向），避免粗粒度分类带来的胡乱推荐；
- 多轮批量测试（26 个专业全链路验证）发现，英语、日语等外语专业原本落在「人文社科」方向，拿到的是「现代汉语」「中国古代文学」这类汉语言文学课程。修复方式是把外语类拆成独立方向，规划内容换为综合英语、语音、听力、翻译理论与实践、CATTI 等语言类课程与证书，前端自评模板同步拆出听力、口语、词汇、翻译、写作、二外、跨文化七项。

此外还修复了「换专业残留」问题：学生改专业后，旧方向的自评数据可能仍留在数据库中（前端不再发送该字段，updateById 跳过 null），画像提示词与 Agent 工具原先按「有没有值」而不是「当前方向」选用数据源，会把数据科学学生的画像按残留的医学类自评生成。现在两者都按 `MajorDirection.isIT` 判定当前方向选数据源，保存档案时还会显式清除残留字段。

## 5.3 AI 动态学习计划

每日任务打卡后，下次生成计划时模型会读到最近 14 天的完成率、连续打卡天数与未完成任务列表，据此重新编排后续计划：完成率低时减量，执行稳定时加量，弱项优先。

## 5.4 AI 竞赛推荐

推荐引擎的评分由四部分构成：

| 维度 | 权重 | 说明 |
| --- | --- | --- |
| 专业对口度 | 最高 | 精确对口 +30，不限专业 +4，同大类 +6 |
| 难度匹配 | 次高 | 与学生自评水平匹配才加分 |
| 年级匹配 | 中 | 适合低年级的比赛对高年级不减分，反之则减分 |
| 报名剩余时间 | 中 | 时间充裕加分，已截止直接扣分或排除 |

排序先按对口程度分档，再按分数排——**只按分数排的话，某场面向全校的比赛会因为时间宽裕拿了高分，挤掉真正为本专业而办的那一场。**

竞赛库覆盖 175 个专业，每个专业平均 16.7 场精确对口的赛事（最少 3 场，最多 30 场）。种子数据使用 `MERGE INTO ... KEY(name)` 写入，重复启动不会造成重复数据。

推荐结果不止于「告诉你报哪个」：列表、详情与推荐接口统一返回 `registrationUrl` / `registrationChannel` / `registrationLabel` / `registrationStatus` / `registrationAction` 五个字段，前端据此渲染报名主按钮与状态标签。解析规则见 5.9 节。

## 5.5 AI 成长助手（核心页面）

五种模式切换，每种模式有不同的人设与快捷提问。**提问列表会根据学生的专业方向动态生成**——不会出现给文科生推荐"讲讲多态"的情况。

页面上的 Agent 元素：

- 回答过程中显示阶段提示（"正在检索知识库…"、"正在整合资料…"）；
- 回答下方是可折叠的执行轨迹卡片：调用了哪些工具、每个工具返回了什么、本次参考了哪些资料、事实验证结果；
- 支持语音输入提问与语音朗读回答。

## 5.6 AI 简历生成

汇总学习记录、成长档案、竞赛与技能，生成 A4 结构化简历。早期版本只有一个
`window.print()` 按钮，在深色主题下打印会得到黑底黑字、还带着顶部导航和工具栏，
"可导出"实际上不可用；作品介绍里写的"在线编辑"也没有对应实现。本次补齐为完整交付链路：

- **在线编辑**：生成后可逐字段修改姓名、意向岗位、学校/专业/年级、个人优势与五类清单
  （专业技能、核心课程、项目、竞赛、证书，用「每行一项」编辑）；`PUT /api/resume` 落库，刷新后不丢失；
- **字段清洗**：服务端只接受 8 个白名单字段，字符串去控制字符并按长度截断，数组去重、去空、
  上限 40 项。`resume.content` 是一整列 JSON，写入任意嵌套结构或超长内容会让下次读取解析失败，
  页面直接退化成一张空白 A4 纸，因此保存前必须收敛结构；
- **三种交付方式**：页面保留深色 A4 预览；「打印 / 导出 PDF」在打印期间给 `body` 加
  `resume-print` 标记，配合全局 `@media print` 切成白底黑字、A4 分页并隐藏导航与工具栏；
  「下载简历文件」生成一份完全独立、内联 A4 样式、不依赖站点任何 CSS 的 HTML，双击即可打开或另存 PDF；
- **异常语义**：未初始化档案时返回 409 业务状态而不是 500，由前端统一引导到档案初始化（见 5.10）。

`ResumeSaveTest` 4 项覆盖白名单、超长截断、控制字符、数组上限与"落库 JSON 可正常读回"。

## 5.7 课程地图与动态背景

- 课程地图按学生真实专业加载，可视化每门课的进度；
- 全站背景是一个纯 Canvas 实现的动态知识网络：漂浮的知识节点（课程 / 技能 / 竞赛 / 规划）按距离连线，光脉冲沿线游走，三团极光缓慢流动，支持鼠标视差。节点数按屏幕尺寸自适应（38~104），DPR 上限 1.6，帧率上限 40fps，页面切到后台自动暂停，并尊重系统的"减少动态效果"偏好设置。

## 5.8 B站课堂（学习资源闭环）

校内课程地图回答"该学什么"，B站课堂回答"去哪学"：

- **资源库规模与覆盖**：262 门公开课，覆盖 13 个类别（大学基础课、编程开发、数据与AI、理工专业课、医学专业课、经管专业课、法政教育、人文艺术、农林生命、设计创作、职场技能、外语提升、考研升学）。**175 个专业全部覆盖，每个专业至少 3 门精确对口课、平均 18.5 门**，茶学、烟草、监狱学、逻辑学这类冷门专业也不会只看到通用课；
- **数据一致性由生成脚本保证**：`scripts/gen-bilibili-seed.py` 是 H2 / MySQL 两份种子 SQL 的唯一生成入口。它从 `database/majors.sql` 读取 175 个专业字典，用学科门类 / 专业组标签展开 `suitable_major`，**任何字典外的专业名直接报错**。早期手写 SQL 里的「应用统计学」「应用心理学」「秘书学」永远无法精确命中，只会被近亲规则蹭成 80 分，这正是「推荐不对口」的根源。脚本还校验标题唯一、字段长度与每个专业的对口课数量，并在 SQL 末尾生成 `DELETE ... WHERE title NOT IN (...)` 清理旧条目——老用户不删 `data/` 目录，重启即可拿到最新的专业映射；
- **贴合度分层**：同为 100 分的课程也要分主次。`sort_order` 按「适配专业数」编码三档：专业核心课（≤20 个专业）、学科方向课（21~40）、门类公共基础课（>40 或 `*`）；`CourseMajorRelevance.fitness()` 再对「标题 / 关键词命中专业核心词」加权（心理学→「心理」、口腔医学→「口腔」、茶学→「茶」）。因此心理学第一屏是普通心理学 / 实验心理学，口腔医学第一屏是口腔解剖生理学，而不是高数、大学化学。公共基础课也按真正需要它的专业精确标注：大学化学只给化工 / 材料 / 农林医方向，不再挂满整个工学门类；
- **推荐位分配**：`BilibiliRecommendPolicy` 由页面与 Agent 工具共用——100 分对口课按贴合度严格占满 16 个推荐位，**不设分类上限**（早期「每类最多 4 条」的多样性规则反而把高数排到了专业课前面）；对口课不足时 80 分近亲最多补 3 门、60 分通用最多补 2 门，且只做补位。宁可少推，不可错推；
- **相关度判定**：`CourseMajorRelevance` 精确对口 100 / 近亲专业 80 / `*` 真通用 60，其余一律跳过。**刻意不复用竞赛的 `CompetitionMajorMatcher`**：竞赛按 19 个学科大类匹配是合理的，但「理科基础类」把 心理/数学/统计 归为一类，套到课程上会把机器学习推给心理学专业；课程推荐只认名字层面的近亲专业，不做学科大类推断；
- **链接策略**：存"课程名 + UP 主"的 B 站搜索直达链接而非固定 BV 号，规避视频下架死链，长期稳定命中正版课程页；
- **Agent 联动**：`search_bilibili_courses` 工具让 AI 助手回答"去哪学"时引用真实课程条目，链接进入「查看依据」可追溯；
- **实现与测试**：`BilibiliResource` + `BilibiliController`（资源列表 / 分类统计 / 个性化推荐）+ `Bilibili.vue` + `BilibiliTool`，配套 24 个单元测试（资源工具 6 项、相关度规则 8 项、推荐位策略 5 项、种子覆盖率 3 项、教资课错配 2 项）。覆盖率测试直接读取生成的 H2 种子 SQL，断言 175 个专业名 100% 属于字典、每个专业至少 3 门对口课、编程课不会蹭到心理学 / 口腔医学。

## 5.9 竞赛报名入口直达

### 问题：官网不等于报名页

竞赛表原本已有 `official_url`，页面也提供「官网」文字按钮，但学生点进去常常是主办单位门户首页：

| 赛事 | 库里的 official_url | 实际报名地址 |
| --- | --- | --- |
| 蓝桥杯 | `https://www.lanqiao.cn/` | `https://dasai.lanqiao.cn/`（大赛报名系统） |
| 传智杯 | `https://www.itcast.cn/` | `https://www.boxuegu.com/match/`（大赛报名通道） |
| 中国大学生计算机设计大赛 | `https://www.jsjds.com.cn/` | `https://jsjds.blcu.edu.cn/`（国赛官网） |

更普遍的情况是：学科竞赛多由学校 / 学院统一组织报名，个人在官网上根本找不到提交入口，需要看本校通知。
因此「报名入口」必须是独立于官网的一层能力。

### 三类渠道与兜底策略

`CompetitionRegistrationLink` 按赛事名在运行时解析，输出统一结构：

| 渠道 | 判定 | 直达目标 |
| --- | --- | --- |
| `ONLINE` | 白名单内有独立在线报名系统 | 官方报名平台（16 个稳定域名，已核实） |
| `NOTICE` | 官网常年发布报名通知 | 官网通知页 |
| `SCHOOL` | 其余赛事（占多数） | 「赛事名 + 报名通知 + 校内选拔」检索结果，一次点击直达通知列表 |

白名单只收录不带届数 / 年份的**稳定域名**（例如挑战杯每年启用 `2025.tiaozhanbei.net`、`2026.tiaozhanbei.net`，
因此统一指向主站 `tiaozhanbei.net`），避免某届赛事结束后链接失效。检索类链接的中文关键词经 `URLEncoder` 编码，
不含空格与未编码汉字，浏览器可直接打开。任何情况下仍保留 `official_url` 作为「官网」次入口，两个链接互相兜底。

### 为什么不落库

报名系统地址每年都可能变化。若把 `registration_url` 写进种子数据，升级时必须同步 H2 / MySQL 两份 SQL，
且老用户的 `data/` 目录会长期留着过期链接。这里把五个报名字段全部做成
`@TableField(exist = false)` 计算字段，由 `apply(Competition)` / `decorate(Map, Competition)` 在返回前统一填充：

- **零表结构变更**：不动 schema、不动种子、不需要用户删库重建，H2 / MySQL / 分布式数据库三档行为一致；
- **一处维护**：新增或修改赛事报名入口只需改白名单常量；
- **全链路一致**：竞赛列表、详情、AI 推荐、Agent 工具 `find_competitions`、离线编排 `OfflineComposer`、
  RAG 语料块都调用同一个策略类，不会出现「页面说官方在线报名、助手说去学校问」的分裂。

### 前端与交互

- 竞赛中心顶部横幅显示「N 场赛事正在报名」，提供「只看报名中」开关；首页「竞赛报名」快捷入口
  通过 `/home/competitions?register=1` 直接落到筛选后的列表；
- 每张卡片与 AI 推荐卡片把原来的「官网」小按钮升级为**报名主按钮**：`ONLINE` 显示「立即报名」，
  `SCHOOL` 显示「校内报名指引」，`UPCOMING` 显示「查看报名安排」，`CLOSED` 显示「报名已结束」（仍可点开查下一届通知）；
  按钮下方标注渠道说明，避免学生误以为点一下就直接提交报名表；
- 卡片增加「报名中 / 已截止 / 即将开放」状态标签；`renderMarkdown` 增加 URL 自动链接化，
  AI 助手回答里的报名入口可直接点击（新窗口打开，`rel=noopener noreferrer`）。

### 验证

`CompetitionRegistrationLinkTest` 9 项覆盖白名单命中、校内检索兜底、通知类赛事、状态边界、按钮文案、
实体与 Map 装饰、不落库约束（反射检查 `@TableField(exist=false)`）、以及**读取生成后的 H2 种子 SQL
逐场校验 101 场赛事都有可点链接**。全新库端到端验证：101/101 场返回完整报名字段，
46 场状态为「报名中」，详情与推荐接口字段一致；4 个官方报名入口实测 HTTP 200；
竞赛页在 1440 / 1280 / 1100 / 900 / 640 五个视口下零重叠、零溢出。

## 5.10 首次使用引导与异常边界

评委常用刚注册的账号直接点各个模块，这条路径以前体验很差：新用户没有档案，
点「生成四年规划」会弹 `服务器内部错误: 请先完善个人档案`，点「生成 AI 简历」更会把
Java 空指针原文 `Cannot invoke "...getMajorId()" because "p" is null` 直接展示在浏览器里；
专业知识地图则显示「课程数据正在补充中，敬请期待」，容易被误认为课程库根本没做完。

本次把「状态」与「故障」彻底分开：

- **`ProfileNotReadyException`（409）**：五年规划、竞赛推荐、学习计划、学生画像、简历生成等
  所有依赖专业/年级的入口统一在方法入口校验，缺档案时抛同一个业务异常。
  `GlobalExceptionHandler` 对 `Exception` 兜底改为「服务端记日志 + 返回稳定通用文案」，
  **不再把 `e.getMessage()` 拼进响应**；内部堆栈只留在日志里。
- **前端统一引导**：`request.js` 识别 409 + 档案相关文案，弹出带「去初始化」按钮的确认框
  （4 秒节流，避免并发请求叠弹窗）；各页面 `catch` 不再重复弹红色错误。
  `MainLayout` 在未初始化时于所有模块顶部显示一条可关闭的引导条。
- **空状态按原因区分**：课程地图区分「还没选专业」（引导初始化）与「该专业数据补充中」，
  不再让评委误判数据完整性；B站课堂与竞赛中心的公开数据在新账号下依旧可正常浏览。

`GlobalExceptionHandlerTest` 4 项钉死异常不外泄、409 可识别、业务文案保留与参数错误映射。

## 6.3 数据库选型与扩展：从 H2 到 MySQL 再到分布式数据库

系统通过 Spring Profile + 环境变量实现了**存储层三档部署能力**，代码零改动即可切换：

| 档位 | 数据库 | 适用场景 | 切换方式 |
| --- | --- | --- | --- |
| 演示档 | H2 内嵌（file 模式） | 评委本机双击即用，免装数据库 | 默认 `demo` profile |
| 生产档 | MySQL 8 | 单机生产、云服务器部署 | `--spring.profiles.active=` 置空 + `DB_HOST/DB_PORT/DB_NAME/DB_USERNAME/DB_PASSWORD` 环境变量 |
| 集群档 | 分布式数据库（TiDB / OceanBase / PolarDB-X 等 MySQL 协议兼容数据库） | 高并发、多节点、需要水平扩展的场景 | 同生产档，只需将连接地址指向分布式集群的接入层 |

### 为什么可以"平滑上分布式"

1. **MySQL 协议兼容是关键设计。** 主流分布式数据库（TiDB、OceanBase MySQL 租户、PolarDB-X、TDSQL 等）都兼容 MySQL 协议与语法，应用侧只需把 JDBC URL 从单机 MySQL 改为分布式数据库的 LB 接入地址（如 TiDB 的 4000 端口 / OB 的 2883 proxy），驱动与 SQL 方言完全一致。本项目数据访问层用 MyBatis-Plus 标准写法，未使用存储过程、触发器等难以水平扩展的特性，天然具备迁移条件。
2. **schema 脚本双轨维护。** `database/schema.sql`（MySQL 版）与 `db/schema-h2.sql`（演示版）保持同构，所有表都带 `IF NOT EXISTS` 与幂等唯一索引迁移（`zhitu_sync_unique`），在分布式数据库上重复执行同样安全。
3. **主键策略预留分片能力。** 业务表主键统一使用 `AUTO_INCREMENT`（单机档），若切换到需要强分片的集群，仅需将 `id-type` 改为 Snowflake 雪花 ID（MyBatis-Plus 一行配置：`id-type: assign_id`），实体类与业务代码无需改动。
4. **读写分离友好。** Agent 工具全部只读 + 独立的写入口（打卡、建档、保存计划），读写比例约 8:2，接入分布式数据库的 TP/AP 分离或只读副本时，把工具查询路由到只读节点即可，无需改代码。
5. **无状态服务层。** 认证用 JWT（不依赖 Session 复制），文件不落本地盘，后端本身无状态——多实例水平扩容只在数据库一侧有状态，而这正是分布式数据库解决的问题。

### 已验证的事实

- H2 演示档与 MySQL 生产档的 SQL 均经过 138 个单元测试与两轮真实部署验证；
- 竞赛/B站资源等种子数据采用幂等 upsert（H2 `MERGE` / MySQL `ON DUPLICATE KEY UPDATE`），两种语法各自经过脚本生成与实测，可在任意档位重复执行；
- Docker Compose 档即 MySQL 8 真实连接验证（`docker-compose.yml` 含健康检查与初始化脚本挂载）。

> 说明：受比赛环境限制，分布式数据库档位未做集群级压测，以上为架构可行性论证与迁移路径说明；单机 MySQL 档为已实测的部署形态。

# 第七章 创新点

## 7.1 技术创新

**1. 工具调用驱动的 AI Native 架构**

不是"把数据塞进 Prompt"，而是让模型显式声明"我要查什么"，执行情况以事件流实时可视化给使用者。这让 AI 的输出从"信不信由你"变成"可以逐条核对"。

**2. 双引擎编排与诚实降级**

无 Key 时自动切到规则编排，**工具数据依旧真实**；页面上如实标注降级状态。功能降级，诚实不降级。这一条直接服务于"AI 是否可信"这个行业级难题。

**3. 轻量事实校验**

不引入昂贵的 NLI 模型，用"最长公共子串 ≥ 3 字 + 停止词过滤"，在毫秒级开销内把明显无出处的说法标出来。工程上的取舍很清楚：宁可漏判，不能把正常答案标成有问题（早期版本就有这个问题，已通过停止词与 3 字阈值修正）。

**4. 一份工具定义、两套协议出口**

同一批工具既服务内部 Agent，也通过 MCP Server 服务外部生态，且 MCP Server 不含业务逻辑，避免了常见的代码分叉问题。

**5. 零依赖 RAG**

字符二元组 + BM25 + 哈希向量，不依赖分词库或向量数据库，可完全离线、秒级构建索引，降低了复现门槛。

## 7.2 应用创新

**1. AI 建议落在学生自己的真实数据上**

推荐的那场竞赛一定能在竞赛中心查到，课程进度一定来自他本人的打卡。这一点听起来平常，但市面上多数"AI 学习助手"做不到——它们给的是通用建议。

**2. 面向所有专业，而非默认你是程序员**

175 个专业全覆盖；`MajorDirection` 与专业匹配器系统性纠偏，不会给文科生讲 408、给医学生推荐 Java 竞赛。这是本作品在"社会价值"上的一个具体落点：让非热门专业的学生也能获得同等质量的指导。

**3. 用拍照录入化解成长档案的空档案难题**

多数平台默认用户愿意手填十几个字段，现实是没人愿意。把这件事压成"拍照 → 自动填好 → 确认"，档案才有内容，后续的简历生成才不是空转。
